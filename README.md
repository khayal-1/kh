# الخيال موتورز | El Khayal Motors

منصة عربية/إنجليزية لمتجر ومعرض موتوسيكلات، تجمع واجهة المتجر العامة مع حسابات العملاء ولوحة تشغيل للمعرض. الواجهة مبنية على HTML وCSS وJavaScript باستخدام Vite، والبيانات والمصادقة والصلاحيات في Supabase. المستودع يحتوي على الموقع، وظائف Supabase الخادمية، سجل ترحيلات قاعدة البيانات، والاختبارات وسير النشر.

- المستودع: <https://github.com/khayal-1/elkhayal-motors>

> هذا الدليل يصف ما يظهر في الشفرة والترحيلات الحالية. وجود كود ميزة لا يعني وحده أن إعدادها الخارجي اكتمل أو أن ترحيلاتها مطبقة على قاعدة البيانات المستهدفة؛ افحص حالة Supabase وإعدادات النشر قبل تشغيل بيئة جديدة أو اعتمادها للإنتاج.

## نظرة عامة على النظام

يتكوّن النظام من ثلاث طبقات مترابطة:

1. **واجهة المتصفح:** صفحة HTML واحدة، تصميم CSS، وتطبيق JavaScript أحادي الصفحة (SPA) يعرض المتجر وصفحات العميل والإدارة دون إطار واجهة ثقيل.
2. **الخدمات والبيانات:** Supabase Auth لتسجيل الدخول والجلسات، وPostgres للجداول والقيود وسياسات Row Level Security (RLS) والدوال المعاملاتية (RPC).
3. **المهام الخادمية:** Supabase Edge Functions للعمليات التي تحتاج أسرارًا أو صلاحيات خادمية، مثل إدارة حسابات الموظفين، مزامنة الصور مع Telegram، وأدوات بيانات المالك.

واجهة العميل تُبنى كملفات ثابتة في `dist/`، لذلك يمكن تقديمها عبر GitHub Pages أو استضافة ثابتة. يجب أن تكون حماية البيانات في قاعدة البيانات وسياسات RLS، لا في إخفاء عناصر الواجهة فقط.

## بنية المشروع

```text
.
├── index.html                       # نقطة دخول الصفحة وهيكل التطبيق
├── app.js                           # التنقل والعرض والتفاعلات ومسارات العمل
├── style.css                        # التصميم والتجاوب والطباعة
├── src/
│   ├── supabase.js                  # إنشاء عميل Supabase وقراءة ملف المستخدم
│   ├── security.js                  # تهريب النصوص والتحقق من روابط الصور
│   └── purchasing-results.js        # معالجة نتائج تحميل التوريد
├── public/
│   ├── branding/                    # الشعار وأيقونات الموقع
│   └── site.webmanifest             # بيانات تثبيت الموقع
├── supabase/
│   ├── migrations/                  # تغييرات قاعدة البيانات مرتبة زمنيًا
│   └── functions/                   # وظائف Deno الخادمية
├── tests/                            # اختبارات Node المعيارية
├── .github/workflows/
│   ├── quality.yml                  # فحوصات Pull Request والفروع
│   └── deploy-pages.yml             # البناء والنشر على GitHub Pages
├── .env.example                     # أسماء متغيرات البيئة المطلوبة، بلا أسرار
├── package.json                     # أوامر المشروع والاعتماديات
├── pnpm-lock.yaml                   # نسخ الاعتماديات المثبتة
└── vite.config.js                   # مسار البناء الخاص بـ Pages وVercel
```

التطبيق يعتمد على `app.js` بوصفه نقطة تنسيق الواجهة؛ الوحدات المساعدة المعزولة موجودة في `src/`. قاعدة البيانات موصوفة في ملفات SQL، بينما لا تُخزّن بيانات العملاء أو المبيعات في ملفات الواجهة أو في localStorage. يُحفظ اختيار اللغة محليًا، وتدير Supabase الجلسة.

## المستخدمون والصلاحيات

تُدار الهوية بواسطة Supabase Auth، وتُقرأ الأدوار من `user_roles`، وملف الحساب من `profiles`، وصلاحيات الموظف من `employee_permissions`. عند إنشاء حساب Auth جديد، ينشئ مشغّل قاعدة البيانات سجل الملف والعميل ويمنح الدور الافتراضي `customer`. لا يختار المستخدم لنفسه دور موظف أو مدير أثناء التسجيل.

الأدوار المستخدمة في سياسات النظام تشمل العميل (`customer`)، الموظف (`employee`)، المدير (`manager`)، المالك (`owner`) والمدير الإداري (`admin`). قائمة الصفحات والصلاحيات الفعلية يحددها الدور والصلاحيات الممنوحة؛ فإخفاء رابط لا يُعد حماية، لذلك تفرض RLS ودوال الخادم التحقق نفسه.

صلاحيات الموظفين القابلة للتعيين تشمل:

- `catalog_view` و`catalog_manage`: الاطلاع على الكتالوج/المخزون وإدارة الطرازات والصور.
- `requests_view` و`requests_manage`: مراجعة طلبات العملاء وتحديث حالتها.
- `customer_data_view`: الاطلاع على بيانات العملاء في النطاق المسموح.
- `sales_manage`: المبيعات ونقطة البيع والتحصيلات ذات الصلة.
- `expenses_manage`: إدارة المصروفات.
- `accounting_view`: قراءة الحسابات والتقارير المالية.
- `finance_manage`: أدوات المالية المتقدمة.

إدارة حساب الموظف وتعيين دوره وصلاحياته تتم عبر وظيفة `manage-staff` بعد التحقق الخادمي من صلاحية المدير/المالك. لا تُرسل مفتاح الخدمة إلى المتصفح.

## الوظائف ومسارات العمل

### المتجر العام والعملاء

- يستطيع الزائر تصفح الدراجات المنشورة، البحث والتصفية وفتح تفاصيل الطراز.
- قسم «تواصل معنا» يعرض بيانات التواصل للزائر غير المسجل. إرسال رسالة من النموذج يتطلب حساب عميل مسجل؛ كما تقيد سياسات قاعدة البيانات الكتابة.
- إنشاء الحساب وتسجيل الدخول يمران عبر Supabase Auth. عند طلب إجراء يتطلب حسابًا، تحفظ الواجهة الإجراء المعلق لإكماله بعد تسجيل الدخول حيث ينطبق.
- العميل المسجل يستطيع إدارة ملفه، إضافة الدراجات إلى المفضلة، إرسال طلب شراء/طلب طراز، ومراجعة طلباته وفواتيره المرتبطة بحسابه.
- طلبات العملاء ورسائل التواصل يمكن للموظفين المخولين مراجعتها وتحديثها. سجل الردود يوثق الردود التي يسجلها الموظف؛ الاتصال الفعلي بالعميل يتم خارجيًا يدويًا عبر القناة المناسبة.
- سجل فواتير العميل لا يضم تلقائيًا كل عمليات البيع النقدية/القديمة: يجب ربط الفاتورة بحساب العميل الصحيح من خلال إجراء إداري مخول.

### الكتالوج والوحدات الفعلية

الطراز في `motorcycles` ليس هو الوحدة المادية نفسها. تمثل `motorcycle_units` كل دراجة بعينها، مع بيانات تعريف مثل رقم الشاسيه VIN ورقم المحرك والباركود والحالة والضمان والعداد عند توافرها. لذلك يجب أن يعكس رصيد الطراز الوحدات الفعلية، وتمنع دوال قاعدة البيانات حالات عدم التطابق أو بيع الوحدة نفسها مرتين.

تتيح صفحات المخزون والإدارة إضافة/تعديل الطرازات، إدارة نشرها، تسجيل وحدات محددة، مراجعة بيانات الوحدات ومسح VIN/الباركود. أدوات المخزون تشمل تكلفة الوحدة وحد إعادة الطلب وتنبيهاته والجرد وتسوية الفرق والضمان وأوامر الصيانة. تسجيل وحدة افتتاحية يتطلب بيانات التكلفة التي تفرضها القاعدة؛ لا تستخدم وحدات تجريبية بدل مخزون حقيقي.

### المبيعات ونقطة البيع

- يمكن لموظف مخول إنشاء فاتورة بيع من نقطة POS مع اختيار الوحدات المادية عند انطباق ذلك، وتسجيل عميل أو عملية بيع مباشرة، وتسجيل دفعة كاملة أو جزئية وطريقة الدفع والحساب المستلم.
- التحصيل اللاحق يضاف إلى الفاتورة من خلال مسار دفعة مستقل ومحمِيّ، مع حماية من تكرار تسجيل الطلب نفسه.
- يعرض النظام الفاتورة، الرصيد، المرتجعات والرصيد الدائن. إصدار الفاتورة أو تسجيل الدفعة في النظام ليس تحويلًا بنكيًا أو تحصيلًا إلكترونيًا؛ على الموظف تنفيذ الدفع/الاسترداد خارج الموقع ثم توثيق ما حدث.
- يمكن إعداد عرض سعر بتاريخ صلاحية وبنود، تحديث حالته إلى مرسل أو معتمد أو ملغى، ثم تحويل العرض المعتمد وغير المنتهي إلى فاتورة. العرض لا يحجز المخزون ولا يخفضه.
- يمكن إنشاء جدول أقساط يدوي مرتبط برصيد فاتورة. يجب أن يساوي مجموع الأقساط الرصيد المستحق، ولا يضيف النظام فوائد أو رسوم تمويل تلقائيًا.
- يمكن تسجيل تسليم الدراجة وإصدار محضر تسليم/إيصال، وطباعة المستندات المخصصة لذلك.
- مرتجع البيع يرتبط بالفاتورة والوحدة الأصلية، ويصنف العنصر صالحًا لإعادة البيع أو تالفًا. لا تزيد الوحدات إلا عند قبول العنصر كصالح. يعالج النظام الرصيد الدائن والاسترداد المحاسبي؛ لا يحول الأموال بنفسه.

### الموردون والتوريد

مسار التوريد هو: إنشاء المورد ← إنشاء أمر شراء وبنوده ← تسجيل استلام جزئي أو كامل ← إضافة حركات المخزون والوحدات حسب ما ينطبق ← تسجيل فاتورة المورد وربطها بالأمر/الاستلام ← تسجيل دفعة المورد ومتابعة الرصيد.

يمكن إدخال فاتورة المورد وربط بنودها بالوحدات، وتسجيل الدفعات الجزئية أو الكاملة ومرجعها. إدخال الفاتورة وحده لا يغيّر المخزون؛ الاستلام هو الذي يضيف الكمية. يمكن تسجيل مرتجع توريد مقابل ما استُلم بالفعل، مع تقييد الكمية بالكمية غير المرتجعة والمخزون المتاح وتسجيل حركة سالبة وائتمان على حساب المورد. بعض السلف يمكن تسجيلها وتخصيصها على فواتير لاحقة؛ السلف غير المرتبطة بفاتورة لها قيود منفصلة موضحة في الحدود أدناه.

### الحسابات والمالية

تشمل الواجهة المالية دليل الحسابات، القيود اليومية وبنودها، الأرصدة وميزان المراجعة، قائمة الدخل والميزانية، دفتر النقدية، أعمار الديون، المصروفات ومدفوعاتها، الحسابات البنكية والخزائن، جلسات النقدية وتسليم العهدة، وإدارة التحصيلات/الاستردادات غير المخصصة.

الأدوات المتقدمة تشمل الفترات المالية وإقفالها، أرصدة افتتاحية متوازنة، مراكز تكلفة، سلف الموردين وتخصيصها، الأصول الثابتة والإهلاك، التسويات البنكية والشيكات، القيود المتكررة، الميزانيات مقابل الفعلي، الاستحقاقات، المصروفات النثرية، وعكس القيود وفق القيود المطبقة. تُنشأ قيود تشغيلية لمصادر مثل المبيعات والتحصيل والمشتريات والمرتجعات، وتُستخدم ترحيلات لتسوية السجلات التاريخية بطريقة قابلة للتكرار.

القيود المنشورة في الدفتر المالي غير قابلة للتعديل المباشر؛ التصحيح يتم بإجراء عكسي أو إجراء محاسبي مناسب. إعداد نسبة ضريبية لا يعني احتسابها آليًا على كل فاتورة ولا إرسال إقرار أو فاتورة إلى مصلحة الضرائب.

### الموظفون والموارد البشرية

وحدة الموارد البشرية تتضمن ملفات الموظفين، ربطًا اختياريًا بحساب دخول الموظف، الحضور والانصراف، طلبات الإجازات ومراجعتها، العهد والتسليم، سلف الموظفين، عمولات المبيعات، مسودات الرواتب، ترحيل الرواتب، المدفوعات الجزئية وقسائم الراتب. يجب إدخال مبالغ الضرائب والتأمينات من جهة مختصة؛ لا يفترض النظام نسبًا قانونية تلقائيًا.

### علاقات العملاء والإدارة

تدعم وحدة علاقات العملاء تصنيف العميل، مصدره وموافقة التواصل، حدود الائتمان، كشف الحركة، سجل التفاعل، الشكاوى وتعيينها، والإشعارات الداخلية. للمالك صفحة أدوات إدارة البيانات والنسخ الاحتياطي والاستعادة وإعادة الضبط؛ هذه عمليات عالية التأثير ومقصورة على المالك.

### الطباعة

زر «طباعة الكشف» العام يظهر فقط في لوحات التقارير التي وُسمت للطباعة، مثل كشوف المخزون والجرد والتكلفة وإعادة الطلب، البيانات المالية والعملاء والمصروفات. طباعة الفاتورة ومحضر التسليم تبقى إجراءات منفصلة في المستندات نفسها. تنسّق قواعد CSS صفحة الطباعة لإخفاء عناصر التحكم غير المطلوبة.

## قاعدة البيانات والأمان

- الترحيلات في `supabase/migrations/` هي سجل تغييرات المخطط والسياسات والدوال؛ تُطبق بالترتيب الذي تديره Supabase CLI وسجل الترحيلات، ولا تُعدّل ترحيلًا سبق تطبيقه على بيئة مشتركة. أضف ترحيلًا جديدًا للتغييرات اللاحقة.
- قاعدة البيانات تستخدم جداول مرتبطة ومفاتيح أجنبية وفحوصات وفهارس ومشغّلات، إضافة إلى RPC للعمليات التي تحتاج ذرّية، مثل البيع والاستلام والمرتجعات والدفعات.
- RLS مفعّلة على بيانات التطبيق الحساسة. سياسات القراءة والكتابة تميز الزائر والعميل والموظف والمدير والمالك، ودوال RPC الخاصة تتحقق من الصلاحية قبل تعديل عدة سجلات معًا.
- الكتالوج المنشور يمكن قراءته للعامة؛ بيانات العملاء والموردين والرواتب والدفاتر الداخلية ليست عامة. لا تضع في README أو الشفرة أرقام هواتف حقيقية أو رموز دخول أو نسخ بيانات فعلية.
- `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` إعدادان يرسلان إلى المتصفح، والمفتاح Publishable/Anon ليس بديلًا عن RLS. لا تضع `SUPABASE_SERVICE_ROLE_KEY` أو كلمات مرور قاعدة البيانات أو رموز Telegram أو OAuth في JavaScript أو `.env.example` أو Git.
- وظائف Edge Functions تستخدم الأسرار الخادمية التي يحق لها الوصول إليها فقط بعد التحقق من هوية المستخدم ودوره/صلاحياته. تعامل مع أي نسخة احتياطية أو سجل مسترجع كمعلومات حساسة.

## التشغيل المحلي

المتطلبات: Node.js 20+ (الفحوصات المنشورة تستخدم Node.js 22)، وCorepack/pnpm. أوامر المشروع المعتمدة في CI تستخدم pnpm.

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env.local
```

املأ `.env.local` ببيانات **البيئة المقصودة** من إعدادات مشروع Supabase:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
```

ثم شغّل الموقع محليًا:

```bash
pnpm dev
```

يفتح Vite عنوانًا محليًا ويطبع الرابط في الطرفية. لإنتاج نسخة محلية:

```bash
pnpm build
pnpm preview
```

إذا لم تُضبط متغيرات Supabase فلن تعمل عمليات المصادقة والبيانات المرتبطة بها. لا تختبر تسجيل عميل أو مبيعات حقيقية على قاعدة الإنتاج؛ استخدم بيئة اختبار وبيانات غير حقيقية. ملفات `.env` و`.env.*` و`node_modules/` و`dist/` مستثناة من Git مع إبقاء `.env.example` فقط.

## Supabase والترحيلات

1. أنشئ/اختر مشروع Supabase مستقلًا لكل بيئة، واضبط URL والمفتاح Publishable في البناء والبيئة المحلية.
2. في إعدادات Auth اضبط Site URL وRedirect URLs لتشمل عناوين الموقع الفعلية؛ عنوان GitHub Pages يتضمن مسار `/elkhayal-motors/`. راجع كذلك مسارات إعادة التوجيه لتأكيد البريد واستعادة كلمة المرور قبل تفعيلها.
3. هذا المستودع يتضمن SQL داخل `supabase/migrations/` لكنه لا يتضمن حاليًا `supabase/config.toml`. عند إدارة المخطط بالـ CLI، جهّز إعداد Supabase CLI المحلي أولًا، ثم اربطه بالمشروع المقصود وسجّل دخول CLI بطريقة آمنة. مثال تسلسلي بعد إعداد CLI:

   ```bash
   npx supabase init
   npx supabase login
   npx supabase link --project-ref <project-ref>
   npx supabase migration list
   npx supabase db push
   ```

   راجع تغييرات CLI الناتجة عن `init` قبل حفظها. افحص قائمة الترحيلات المطبقة والمعلقة قبل `db push`، وخذ نسخة احتياطية من قاعدة الإنتاج قبل أي ترحيل كبير. لا تستخدم مشروعًا أو كلمة مرور من جلسة أخرى، ولا تضع الأسرار في الأمر المحفوظ أو المستودع.
4. انشر Edge Functions التي تحتاجها من `supabase/functions/` إلى مشروع البيئة، واضبط أسرارها في Supabase Dashboard/CLI حسب التوثيق أدناه. نشر الملفات وحده لا يضيف هذه الأسرار ولا يشغّل ربط Telegram.
5. اختبر التسجيل، الدخول، عرض الكتالوج، الصلاحيات وعمليات العمل في بيئة اختبار. افحص سجلات Supabase Auth وFunctions وPostgres عند الفشل، وتأكد من تطبيق الترحيلات على **المشروع نفسه** الذي تستخدمه الواجهة.

ملفات الترحيل مقسمة إلى مجموعات تطورت مع المشروع: الأساس والمصادقة وRLS، الكتالوج والطلبات والمراسلات، POS والموردون والمرتجعات، الوحدات المادية وربط VIN بالمبيعات، المالية والقيود، الموارد البشرية، المخزون/الجرد/الضمان/الصيانة، أدوات المالك، ومزامنة الصور. أسماء الملفات وترتيبها الزمني هي المصدر الكامل للتفاصيل الدقيقة.

## الصور وTelegram

الصورة التي يرفعها موظف مخول تمر عبر `telegram-photo-upload`، الذي يتطلب جلسة مستخدم وصلاحية إدارة الكتالوج، ثم يستخدم `TELEGRAM_BOT_TOKEN` و`TELEGRAM_CHAT_ID` من أسرار Edge Function للتواصل مع Telegram وتسجيل مرجع الأصل. توجد وظيفة `telegram-photo-sync` لمزامنة/استكمال بيانات أصول الصور؛ تفاصيل التخزين ومراجع Telegram موثقة في ملفات الدوال والترحيلات المتعلقة بها.

لتفعيل المسار: أنشئ بوت Telegram، أضفه إلى وجهة الصور المطلوبة، ثم انشر الدوال واضبط `TELEGRAM_BOT_TOKEN` و`TELEGRAM_CHAT_ID` في أسرار Supabase فقط. لا تضع الرمز في `app.js` أو متغير `NEXT_PUBLIC_*`. تحقق من وصول الصورة ومن ربطها بالطراز الصحيح قبل استخدامها في إعلان؛ الصور المرجعية لطراز عام لا تثبت أنها صورة الوحدة المعروضة للبيع.

## الاختبارات والبناء

```bash
pnpm check    # فحص صياغة app.js ووحدات Supabase والأمان
pnpm test     # اختبارات Node المعيارية
pnpm build    # إنتاج dist عبر Vite
```

الاختبارات الحالية تتضمن `tests/security.test.js` للتحقق من تهريب/تنقية مدخلات وروابط غير آمنة، و`tests/purchasing-results.test.js` لمعالجة نتائج تحميل بيانات التوريد. لا تغطي هذه المجموعة وحدها كل تكاملات Supabase أو كل تدفقات الواجهة؛ أضف اختبارًا مع كل منطق حرج جديد واختبر RPC/RLS في بيئة مرحلية.

GitHub Actions workflow المسمى **Quality checks** يعمل عند فتح Pull Request إلى `main` وعند الدفع إلى `main` أو فروع `fix/**` و`feature/**`. يثبت الاعتماديات من lockfile، يشغل فحص الصياغة والاختبارات وتدقيق اعتماديات الإنتاج ثم البناء. نجاح هذا الـ CI لا يثبت وحده سلامة إعدادات Auth أو تطبيق migrations أو عمل خدمة خارجية.

## النشر

### GitHub Pages

الطريقة الموصولة في هذا المستودع هي GitHub Pages. ملف `.github/workflows/deploy-pages.yml` ينشر تلقائيًا بعد الدفع إلى `main`، ويمكن تشغيله يدويًا من GitHub Actions. يقوم الـ workflow بالبناء بـ pnpm ثم يرفع `dist/` وينشرها على Pages. يضبط `vite.config.js` المسار الأساسي `/elkhayal-motors/` لصفحة المشروع، وملف الإعداد ينتج المسار `/` عندما يبني بيئة Vercel.

مسار الإصدار المعتاد:

1. أنشئ فرعًا من `main` للتغيير.
2. نفّذ `pnpm check` و`pnpm test` و`pnpm build`.
3. افتح Pull Request إلى `main` وراجع فحوصات Quality checks.
4. بعد الدمج، راقب **Deploy website to GitHub Pages** حتى ينجح، ثم افتح رابط الموقع وتحقق من الميزة المتأثرة.

النسخة المبنية محليًا لا تعني أنها نُشرت. النجاح يتطلب دمج التغيير وتشغيل نشر Pages والتحقق من مخرجاته. بعد تغييرات قاعدة البيانات تحقق كذلك من ترحيلات Supabase، فهي نشر منفصل عن ملفات الموقع.

### Vercel

يمكن توصيل المستودع بمشروع Vercel للبناء الثابت: أمر البناء `pnpm build` ومجلد الإخراج `dist`. إعداد `vite.config.js` يختار `/` عند وجود متغير `VERCEL`. لا يحتوي المستودع ملف `vercel.json`، لذا تُضبط إعدادات المشروع ومتغيراته ونطاقاته داخل Vercel. لا تفترض أن النشر على Vercel تم لمجرد دعم إعداد المسار في Vite؛ سير النشر التلقائي الموثق هنا هو GitHub Pages.

## النسخ الاحتياطي والتشغيل الآمن

وظيفة `owner-data-management` مقصورة على المالك وتضم مسارات النسخ الاحتياطي والاستعادة وإعادة ضبط البيانات التشغيلية. النسخة الاحتياطية تحتوي بيانات تشغيلية حساسة؛ احفظها في مكان محمي ولا ترفقها علنًا. الاستعادة مرتبطة بنسخة/بنية المشروع وتتحقق من صيغة النسخة وبصمتها ومراجع Auth قبل استدعاء دالة الاستعادة. إعادة الضبط أو حذف بيانات الحسابات إجراء هدّام لا تستخدمه للاختبار.

قبل تحديث قاعدة الإنتاج: خذ نسخة احتياطية قابلة للاسترجاع، راجع الترحيلات المعلقة، اختبرها على بيئة مرحلية، وتحقق من التقارير وسجلات التدقيق بعد التطبيق. لا تُعد تشغيل عملية كتابة ذات نتيجة غير معروفة قبل فحص حالة السجل؛ بعض إجراءات الدفع والاستلام مصممة لدعم المحاولات الآمنة، لكن هذا لا يغني عن التحقق.

## حدود التنفيذ الحالية

- لا يوجد تكامل بوابة دفع يخصم المال أو يحول المبالغ؛ الدفع والاسترداد يُنفذ خارج الموقع ثم يوثّق الموظف النتيجة.
- لا توجد رسائل آلية جاهزة للعميل عبر WhatsApp أو SMS أو البريد التشغيلي؛ واجهة الإدارة تعرض قنوات الاتصال وتسمح بتسجيل الرد، لكن الإرسال الفعلي يعتمد على إعداد مزود أو يتم يدويًا.
- Telegram يحتاج بوتًا ووجهة صحيحة وأسرارًا خادمية وEdge Functions منشورة؛ وجود صور في قاعدة البيانات لا يعني أن كل صورة وصلت أو ارتبطت بالوحدة الصحيحة.
- إعداد معدلات الضريبة لا يفعّل احتسابًا آليًا على كل المبيعات والمشتريات ولا تكاملًا مع ETA.
- عروض الأسعار لا تحجز المخزون. أقساط الفواتير لا تتضمن فائدة أو رسومًا تلقائية.
- لا تتحول كل فاتورة قديمة أو بيع مباشر إلى سجل فواتير عميل تلقائي؛ الربط بالحساب مقصود ويجب أن يكون صحيحًا.
- قد تختلف حالة الموقع الحي عن الشفرة إذا كانت ترحيلات Supabase أو مفاتيح البيئة أو إعدادات Auth غير محدثة. تحقق من كل من إصدار الواجهة وحالة قاعدة البيانات قبل اعتبار ميزة تشغيلية مكتملة.

## إضافة ميزة أو تعديلها

1. حدّد شاشة المستخدم ومسار البيانات والصلاحيات المطلوبة قبل تعديل الواجهة.
2. أضف/عدّل SQL في **ترحيل جديد**، مع المفاتيح والقيود والفهارس وRLS ودوال RPC اللازمة؛ لا تعتمد على شرط JavaScript وحده لحماية البيانات.
3. أضف منطق الواجهة في `app.js` أو الوحدة المناسبة في `src/`، واستخدم `esc` و`safeImageUrl` عند إدراج محتوى غير موثوق في HTML.
4. أضف اختبارًا للوظيفة، وخاصة منع التكرار أو تجاوز الصلاحية أو اختلال الرصيد في العمليات المالية والمخزنية.
5. اختبر على بيانات مرحلية، ثم افتح Pull Request. بعد الدمج تابع نشر Pages، وطبّق ترحيل Supabase المناسب بصورة منفصلة، ثم اختبر النتيجة الحية.

المبدأ التشغيلي الأساسي: احفظ السجل المصدر، واربط كل حركة مالية أو مخزنية بمستندها ووحدتها، واستخدم الإلغاء/العكس أو الحذف المنضبط بدل محو التاريخ المحاسبي.
